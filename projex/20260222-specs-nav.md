## Vision

The ZOH specs are the authoritative source for what the language *is* (`spec/`) and how to build a runtime (`impl/`). Together they form a complete, self-consistent reference that any implementer can follow to produce a compliant runtime. The goal is a spec pair that is gap-free, internally consistent, aligned with each other, and current with the design decisions made during implementation.

---

## Current Position

**As of 2026-02-22:**

The language spec (`spec/`) is substantially complete — verbs, types, expressions, and core behaviors are well-defined across eight files (~2600 lines). The impl spec (`impl/`) covers the full pipeline from lexer to validation (13 numbered files). ## Roadmap

### Phase 1: Impl Spec — Scenario Coverage — [Status: Current]

**Goal:** Execute the three ready scenario spec plans to establish conformance test coverage for complex state, concurrency, and security.

**Milestones:**
- [ ] **Card Battler scenario spec** — State integrity benchmark: nested collections, object references, cyclic references, recursion limits
  - Execution: `20260215-card-battler-scenario-spec-plan.md`
- [ ] **Ecosystem Simulation scenario spec** — Concurrency fairness benchmark: 100+ concurrent contexts, shared state contention, memory stability
  - Execution: `20260215-ecosystem-sim-scenario-spec-plan.md`
- [ ] **Metagame Tutorial scenario spec** — Security benchmark: injection attacks, system access, stack overflow resilience
  - Execution: `20260215-metagame-tutorial-scenario-spec-plan.md`

**Exit Criteria:** `impl/scenarios/` contains three completed scenario specs, each with full ZOH source and assertion definitions.

### Phase 2: Impl Spec — Design Currency — [Status: Next]

**Goal:** Absorb recent design decisions from completed evals into the impl spec so it accurately reflects the intended architecture.

**Milestones:**
- [ ] **IClock abstraction** — Add `clock: IClock` to `RuntimeConfig`; replace bare `now()` calls in `Context.block()` and `Runtime.tick()` with `runtime.clock.now()`; extend "Execution Model Compatibility" section with Simulated Time model (host-driven `ManualClock`)
  - Ideation: `20260222-engine-time-awareness-eval.md`
  - Execution: (plan needed)
- [ ] **Async execution model annotation** — Document the async-native execution model (`ValueTask<VerbResult>`) as a recognized alternative to the tick-loop in `impl/09_runtime.md`; annotate the C# reference implementation's departure from the tick-loop model
  - Ideation: `20260222-verb-driver-sync-eval.md`
  - Execution: (plan needed)

**Exit Criteria:** `impl/09_runtime.md` reflects the full Continuation + IClock architecture and documents the async alternative model. No open eval findings remain untranslated into spec text.

### Phase 3: Language Spec — Gap Filling — [Status: Future]

**Goal:** Complete known gaps and perform a thorough audit of the language specification.

**Milestones:**
- [ ] **Standard Preprocessors** — Define the standard preprocessors in `spec/3_runtime.md` (currently `TODO`)
- [ ] **Standard Compilers** — Define the standard compilers in `spec/3_runtime.md` (currently `TODO`)
- [ ] **Language spec audit** — Survey all `spec/` files for gaps, ambiguities, and missing edge cases; produce a findings list for follow-up plans

**Exit Criteria:** No `TODO` markers remain in `spec/`. All standard extension points (preprocessors, compilers) are specified. Audit findings are captured as projex.

---

### Phase 4: Coherence — Cross-Validation — [Status: Future]

**Goal:** Verify that the language spec and impl spec are fully consistent with each other, and that known implementation departures are explicitly documented.

**Milestones:**
- [ ] **Spec/Impl alignment audit** — Cross-validate `spec/` against `impl/` for divergences in type system, verb behaviors, error codes, and execution semantics
- [ ] **C# departure documentation** — Document in the impl spec that the C# reference implementation uses async-native execution instead of the tick-loop model; ensure no implementer is misled by the spec's tick-based pseudocode
- [ ] **Red-team findings remediation (spec-level)** — Address any remaining red-team findings (`20260207-spec-impl-redteam.md`) that have spec-level implications (not already addressed by C# Phase 5)

**Exit Criteria:** Language spec and impl spec are consistent. All known implementation departures are explicitly noted in the impl spec.
